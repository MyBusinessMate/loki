# THREAT-MODEL.md: Loki Password Manager Security Threat Model

## 1. System Overview & Trust Boundaries
Loki is a zero-knowledge agency password manager designed so that client secrets are never transmitted, cached, or decrypted on the server.
- **Client Boundary**: Trusted client runtime where WebCrypto/libsodium executes cryptographic key derivations, encryption, and decryption in memory. Master password and unencrypted DEKs (Data Encryption Keys) reside strictly within this boundary and are never transmitted.
- **Transport Boundary**: TLS 1.3 enforced over all API interactions.
- **Server Boundary**: Semi-trusted orchestration server. Manages authentication, organization membership, RLS authorization policies, wrapped key distribution, and ciphertext blob persistence.
- **Storage/Database Boundary**: Untrusted storage layer containing encrypted blobs, wrapped key structures, audit logs, and operational metadata. Compromise of database or backups reveals zero plaintext secrets.

## 3. Known Architectural Limitations
1. **Compromised Host / Modified JavaScript**: If the deployment server itself is fully compromised and serves modified client JavaScript, zero-knowledge guarantees can be subverted at the browser boundary. Protection: Subresource Integrity (SRI), immutable Docker images, strict reverse proxy CSP.
2. **Browser Memory Hygiene**: JavaScript runtimes do not guarantee instantaneous zeroization of garbage-collected strings. Mitigation: In-memory arrays cleared via `crypto.getRandomValues()` on lock, keys held in transient typed arrays (`Uint8Array`).
